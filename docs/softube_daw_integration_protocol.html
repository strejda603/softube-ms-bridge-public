1 Introduction

1.1 Definitions, Acronyms, and Abbreviations

Acronym Definition
C1 Console 1 Mixing System
OSD The Console 1 On-Screen Display app

1.2 Audience

DAW software developers that want to integrate with the Console 1 system.

2 Overview

2.1 Protocol Overview

The Softube DAW Integration Protocol (SDIP) is a JSON based protocol that enables the Console 1 system to display info about, and control, the tracks of a DAW session. The initial release uses JSON over MIDI SySex as the chosen method of communication, but the protocol might be extended to run over networking sockets or other means of communication in the future.

After a handshake with some version handling and settings, each message describes one or more property changes for a track, such as name or volume. Where applicable, the very same messages can be sent from Console 1 to the DAW, i.e., the user moves a fader ➡ C1 sends an update request to the DAW ➡ the DAW sends back the resulting property change. Numerical properties are just JSON floats with non-specified precision, 0-1 for pan, the value in dB for volume and sends, etc.

Except for the handshake the protocol itself can be seen as stateless, as each message is independent from each other. The DAW transmit changes to tracks as they happen, and vice versa the Console 1 system transmit changes as they happen (faders moved, knobs turned).

2.2 Design Goals

The protocol should be somewhat easy to both generate and parse. While not the most bit efficient approach the JSON in ASCII over SysEx used is very easy to parse for humans using MIDI Monitors or other simple tools.

3 MIDI Ports

The current version of the Console 1 hardware exposes several MIDI ports to the system. However, users of the DAW integration protocol should communicate with only one port, even if multiple hardware devices are present. The port to use is named as follows:

Windows Macos
Console 1 Channel Mk III Console 1 Channel Mk III DAW
Console 1 Fader Mk III Console 1 Fader Mk III DAW

One proven, albeit somewhat clumsy, method for handling port naming differences between operating systems is to utilize the handshake (and optionally SysEx Identity Requests) described below. This allows you to identify the port where the Console 1 system responds to the handshake with ack=true and continue using only that port.

Pseude code:

for each port whose name starts with `Console 1 Channel Mk III` or `Console 1 Channel Mk III`:
   (optionally) send SysEx Identity Request and wait for correct reply
   Initiate handshake, if ack=true from Console 1, this was the correct port and no further iteration is needed.

4 SysEx Identity Request

To help identify the correct port, Console 1 replies to standard SysEx Identity Requests.

However, the Manufacturer ID, family code, model number, and version are likely to change in the future as the API stabilizes.

5 SysEx byte format

Byte Content Description
0 0xF0 SySex start
1 0x7D MIDI Manufacturer ID
2 ‘s’ Four byte magic string “stc1”
3 ‘t’
4 ‘c’
5 ‘1’
n - JSON Message
-1 0xF7 SySex end

6 The Track ID string

All JSON messages in both directions that change track properties use a string called trackId as the key to identify the track.

This string must also be communicated to any Console 1 VST3 plugins in the project via the standard VST3 API, using the kChannelUIDKey as documented here.

Console 1 requirements for the Track ID string: * String defined by the DAW for each track * Unique for every track in a given project * Do not have to be saved with the project; the ID string can be generated on the fly when new tracks are added * Once set, the ID must not change for a track during the current project session.

Many DAWs usually have some internal functionality for identifying tracks that doesn’t rely on track number or any other of the track properties, that can be reused for this.

The Track ID is required to enable the Console 1 system to maintain a link between the Console 1 plugin and tracks created using the API described in this document. This link ensures consistency even when tracks are moved within the project, a process that often leads to asynchronous updates to tracks and associated plugins.

7 JSON String values

In this protocol, the JSON messages are composed of only 7-bit ASCII characters and can be sent as-is, except for the track name and ID string values, which can contain any string set by the DAW (or even by the DAW end user in the case of the track name).

Since the most significant bit of every byte in MIDI SysEx messages must be cleared, special care must be taken when sending strings or data with the most significant bit set.

If a character is not a 7-bit ASCII character, it should be escaped using the syntax specified for JSON (ECMA 404), i.e., the character is converted to UTF-16, and the Unicode code point is escaped as \uAB or \uABCD. For example, Ö becomes \u99, and ピ becomes \u30d4.

If the track name is “ピアノと弦”, it should be escaped as:

{
    "trackId": "ABCDEFG",
    "name": "\u30d4\u30a2\u30ce\u3068\u5f26"
}

8 Float values as dB

Volume and sends typically range from -∞ to a DAW-specific maximum value, such as +6 dB or +12 dB. The default is +6 dB but should be configured per track using the maxVolumeValue and maxSendValue properties if it differs from +6 dB.

-∞ is handled by changing the datatype to a string instead, see:

{
    "trackId": "ABCDEFG",
    "volume": "-Infinity"
}

And this is also what C1 outputs.

C1 can also parse messages handling infinity like in in JavaScript, i.e.

{
    "trackId": "ABCDEFG",
    "volume": -Infinity
}

Note that this not entirely valid JSON and might take some extra effort to get through your JSON generator.

9 Color

The color property is RGB encoded in an int32.

JS example on how to encode separate values:

function colorToNumber(r, g, b) {
    var newColor = 0
    newColor |= ((r * 0xFF) << 0)
    newColor |= ((g * 0xFF) << 8)
    newColor |= ((b * 0xFF) << 16)
    return newColor
}

10 Parsing strategy (from a DAW perspective)

  1. Check magic string
  2. Is this a command message (contain a non-empty cmd property)?
    1. If RESET, start handshake
  3. Is this a handshake reply (contains a non-empty handshake property)?
    1. Check ack value and start sending track updates if true.
  4. Is this a track info update from C1 (contains a non-empty trackId property)?
    1. Parse and apply to DAW state

11 JSON Examples

Newlines and indentation added for clarity.

11.0.1 OSD restart. The DAW should begin the handshake.

Needed as the MIDI port is always online so no way to detect connection.

Console 1 ➡ DAW

{
 "cmd": "RESET"
}

Can also be sent DAW ➡ Console 1 to remove all tracks (also done by handshake).

11.0.2 Handshake request

DAW ➡ Console 1

{
    "handshake": {
        "dawName": "FastTracker 2",
        "protocolVersion": [
            1,
        ]
    }
}

If protocol 1.2 is needed:

{
    "handshake": {
        "dawName": "FastTracker 2",
        "protocolVersion": [
            1,
            2
        ]
    }
}

11.0.3 Handshake reply

Console 1 ➡ DAW

{
    "handshake": {
        "ack": true
    }
}

If OSD doesn’t support a requested API version it will return false.

11.0.10 Keep-alive (ping/pong)

Not yet implemented in C1.

In the direction Console 1 ➡ DAW this is useful to not leave ghost tracks in C1 if the DAW crashes/fail to send reset on exit.

Console 1 ➡ DAW

{
    "cmd": "PING"
}

DAW ➡ Console 1

{
    "cmd": "PONG"
}

11.0.11 Insert Console 1 plugin last in inserts

Not yet implemented in C1. If true, the DAW should insert the Console 1 plugin last in the inserts.

Console 1 ➡ DAW

{
    "trackId": "ABCDEFG",
    "plugin": true
}
